## 4. Marker mechanism, the Lean API it relies on, and why it sees earlier commands' errors

Each consumer's final `#eval show CommandElabM Unit` command computes `fileClean`: it takes its own input context's source text (`Command.Context.fileMap.source`), finds its own extent by re-parsing the command at `cmdPos` with `Lean.Parser.parseCommand` under the current environment and scope, blanks that extent with spaces (line breaks kept), parses the header with `Lean.Parser.parseHeader`, imports with `Lean.Elab.processHeader` (same trust level and main module, `leakEnv := true`), elaborates every command with `Lean.Elab.IO.processCommands` under the frontend's options (`Elab.async` and `internal.cmdlineSnapshots` true), and requires `MessageLog.hasErrors` to be false for the header messages and for the returned command state's messages. In the pinned toolchain (`Lean/Elab/Frontend.lean` lines 94-122, verified in the second session) `IO.processCommandsIncrementally` returns a command state whose `messages` is the fold of `diagnostics.msgLog` over every snapshot of the tree (`toSnapshotTree initialSnap |>.getAll`, which also forces asynchronously elaborated proofs), the same predicate `runFrontend` uses for the exit code. Why the command cannot read earlier errors from its own state: `Lean/Language/Lean.lean` line 749 (`doElab`) sets `messages := .empty` before each command, so the marker command's `(← get).messages` never contains an earlier command's error (the first session verified a naive check is blind on a toy file). The marker prints only if `fileClean` and the existing witness condition (a witness that exists and collects no `sorryAx`; for the builder `consumerGuards`, for the stage consumer `stageGuards` with its two existing diagnostics kept) hold; no diagnostic is added, so registered failing line sets are unchanged. Recorded boundary: an explicit placeholder proof in a declaration the witness does not reference is a warning, not an error, and does not suppress the marker (toy variant h; the gate hygiene scan covers `RMQ/`). Cost: the builder consumer 3.46 s to 10.95 s and the capstone consumer 56.09 s to 120.58 s on this host (base blobs and tip run in one queue on one build).
